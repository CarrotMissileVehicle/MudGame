# MUD 游戏测试目录总览

本目录按模块组织 MUD 项目的测试方案与用例设计文档，遵循 **模块 → 测试层级** 的分层约定。
每个模块目录下再按测试层级细分，例如语法级（syntax）、语义级（semantic）、上下文级（context）、逻辑级（logic）。

## 目录结构

```
tests/
├── README.md                     # 本页：总览、分层约定、通用通过标准、风险提示
└── <module>/                     # 按模块（如 cmdparser / mining_controller / timeservice ...）
    ├── README.md                 # 模块范围、命令清单、输入输出口径、数据依赖
    ├── syntax/                   # 语法级：分词、空白、大小写、别名、缺省、非法字符
    │   └── cases.md
    ├── semantic/                 # 语义级：参数识别、取值范围、资源/类型语义
    │   └── cases.md
    ├── context/                  # 上下文级：玩家状态、权限、采矿硬直拦截
    │   └── cases.md
    └── logic/                    # 逻辑级：后端分发、环境作用域、资源存在性、方向可达
        └── cases.md
```

> 层级命名可随模块规模裁剪：小模块可合并，大模块可增加 `integration/`（跨模块链路）。

## 分层说明

| 层级 | 主题 | 典型验证点 |
| --- | --- | --- |
| 语法级 | 文本如何被切分与规范化 | 分词、空白/Tab、大小写、缩写别名、句法错误、异常字符 |
| 语义级 | 参数值是否被正确解释 | 必填/可选参数、取值范围、类型、资源/指令语义匹配 |
| 上下文级 | 玩家与全局状态是否拦截命令 | 眩晕、死亡、采矿中（硬直）、权限门槛 |
| 逻辑级 | 命令是否路由到正确后端并被环境校验 | 分发命中、后端调用是否发生、作用域/资源/方向校验 |

## 用例编号规范

统一采用 `MOD-POS-SEQ` 三段式编号：

- `MOD`：模块缩写（命令解析器 = `CP`）
- `POS`：层级代码（语法 `S`、语义 `M`、上下文 `C`、逻辑 `L`）
- `SEQ`：三位序号，如 `001`

示例：`CP-S-001`、`CP-M-012`、`CP-C-003`、`CP-L-008`。

## 通用通过 / 失败判定标准

对每类测试按以下指标判定（具体到用例另附预期）：

1. **解析结果（语法）**：返回的 `Command`（verb / args / options / raw）与预期一致；空行返回空 verb；解析错误返回 `verb="error"`；`--help` 返回 `verb="help"`。
2. **返回值 / 提示（语义与上下文）**：`HandlerResult`（`Ok / UnknownCommand / BadArgument / Failed`）及面向玩家的反馈文本符合预期。
3. **后端调用是否发生（逻辑）**：用 handler 是否被调用 + 调用实参来判定错误路径是否被正确拦截（错误路径上 handler **必须不得**被调用）。
4. **日志记录**：关键命令（启动/停止/异常/拦截）产生可校验的日志条目。
5. **异常处理**：任何输入（超长、注入、Emoji、越界）均不导致进程崩溃、不产生未捕获异常、不误分发。
6. **副作用校验**：状态机跃迁（Idle ↔ Mining）与产出结算只在合法路径发生，无重复结算或漏结算。

## 风险提示

- 当前命令 schema 为**点分动词**（如 `mine.start --layer 2`），非空格动词形式；
  需求中提到的空间指令（`mine iron` / `go north` / `time` …）属于**目标形态**，与现行 verb 的映射见各模块 README。
- CLI11 的子命令大小写匹配行为与 Connector 层的大小写不敏感路由**不在同一层**，相关用例已标注“需确认”。
- 别名（`m`→`mine`、`n`→`north`）当前未实现，相关用例标注为“仅当系统支持别名时执行”。
- 本目录为**测试方案与用例设计**文档；自动化可执行代码由各模块后续按层级承接（见各 README “执行前准备”）。
